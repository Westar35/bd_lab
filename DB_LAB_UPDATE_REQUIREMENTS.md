# DB Lab Project Update Requirements

## 0. Назначение файла

Этот файл — обязательное техническое задание для доработки уже существующего учебного Go web-проекта по лабораторной работе по базам данных.

Текущий проект уже реализован и использует только **PostgreSQL**. Его нужно обновить так, чтобы он соответствовал новым требованиям сдачи лабораторной работы:

1. использовать **две СУБД**: PostgreSQL и MySQL;
2. иметь возможность переключаться между PostgreSQL и MySQL через web-интерфейс;
3. поддерживать полное редактирование **абсолютно всех таблиц** через HTML-интерфейс;
4. поддерживать связанные каскадные поиски и зависимые выпадающие списки;
5. не заставлять пользователя искать данные по техническим `id`;
6. иметь понятные маски, placeholder'ы и подсказки в полях ввода;
7. позволять добавлять новые значения справочников прямо из форм основных сущностей через кнопку `+`;
8. сохранять уже введённые данные формы при переходе к созданию связанной записи.

Проект учебный. Приоритет — демонстрация возможностей БД, web-доступа, связей таблиц, CRUD-операций, поисков, отчётов и работы с двумя СУБД. Не нужно чрезмерно упрощать функциональность под «реальную эксплуатацию». Некоторые функции нужны именно для сдачи лабораторной работы.

# 1. Главная цель обновления

Нужно доработать существующий проект так, чтобы web-приложение могло работать с двумя одинаковыми базами данных:

- **PostgreSQL**;
- **MySQL**.

Обе базы должны иметь одинаковую логическую структуру, одинаковые таблицы, одинаковые связи, одинаковые справочники и сопоставимый набор seed-данных.

Пользователь должен иметь возможность переключаться между активной СУБД прямо в web-интерфейсе.

Пример интерфейса:

```text
Активная база данных: PostgreSQL
[Переключить на MySQL]
```

После переключения:

```text
Активная база данных: MySQL
[Переключить на PostgreSQL]
```

После переключения все страницы, формы, списки, CRUD-операции, поиски, API-endpoints и отчёты должны работать уже с выбранной СУБД.

# 2. Обязательное требование: две одинаковые БД

## 2.1. Общий принцип

Нельзя просто добавить MySQL «для галочки». Обе базы данных должны быть реально рабочими.

Требуется:

- PostgreSQL остаётся рабочей СУБД;
- MySQL добавляется как вторая рабочая СУБД;
- схема PostgreSQL и схема MySQL должны быть функционально одинаковыми;
- все основные таблицы должны существовать в обеих СУБД;
- все справочники должны существовать в обеих СУБД;
- все связи должны быть воспроизведены в обеих СУБД;
- seed-данные должны загружаться в обе СУБД;
- приложение должно уметь читать и писать данные в обе СУБД;
- переключение между БД должно происходить без перезапуска приложения.

## 2.2. Поведение при выбранной PostgreSQL

Если пользователь выбрал PostgreSQL:

- списки показывают данные из PostgreSQL;
- создание записей выполняется в PostgreSQL;
- редактирование выполняется в PostgreSQL;
- удаление выполняется в PostgreSQL;
- поиск выполняется в PostgreSQL;
- отчёты строятся по PostgreSQL;
- JSON-endpoints для зависимых dropdown'ов берут данные из PostgreSQL.

## 2.3. Поведение при выбранной MySQL

Если пользователь выбрал MySQL:

- списки показывают данные из MySQL;
- создание записей выполняется в MySQL;
- редактирование выполняется в MySQL;
- удаление выполняется в MySQL;
- поиск выполняется в MySQL;
- отчёты строятся по MySQL;
- JSON-endpoints для зависимых dropdown'ов берут данные из MySQL.

## 2.4. Как хранить выбранную СУБД

Выбранную СУБД нужно хранить на уровне пользователя.

Допустимые варианты:

- cookie `active_db=postgres` / `active_db=mysql`;
- server-side session;
- session value `active_db`.

Недопустимо:

- хранить выбранную БД только в глобальной переменной на весь сервер, если это ломает поведение для разных пользователей;
- требовать перезапуск приложения для переключения;
- переключать БД через изменение `.env`;
- переключать БД только через терминал.

## 2.5. Route для переключения БД

Нужно добавить route для переключения активной СУБД.

Допустимые варианты:

```text
POST /switch-db
GET /switch-db?db=mysql
POST /settings/database
```

При переключении нужно:

1. проверить, что запрошенная СУБД допустима: `postgres` или `mysql`;
2. сохранить выбор в cookie/session;
3. показать flash-сообщение или уведомление;
4. вернуть пользователя на предыдущую страницу или на главную.

Пример сообщения:

```text
Активная база данных изменена на MySQL.
```

# 3. Требования к поддержке MySQL

## 3.1. Go-драйвер

В проект нужно добавить поддержку MySQL-драйвера.

Допустимый драйвер:

```text
github.com/go-sql-driver/mysql
```

Для PostgreSQL оставить текущий рабочий драйвер проекта. Если используется `pgx`, оставить `pgx`. Если используется `lib/pq`, оставить `lib/pq`, если он стабильно работает.

## 3.2. Конфигурация

В `.env.example` должны быть настройки обеих СУБД.

Пример:

```env
APP_PORT=8080

POSTGRES_HOST=postgres
POSTGRES_PORT=5432
POSTGRES_DB=fleet_db
POSTGRES_USER=fleet_user
POSTGRES_PASSWORD=fleet_password
POSTGRES_SSLMODE=disable

MYSQL_HOST=mysql
MYSQL_PORT=3306
MYSQL_DATABASE=fleet_db
MYSQL_USER=fleet_user
MYSQL_PASSWORD=fleet_password
MYSQL_PARSE_TIME=true
MYSQL_LOC=Local

DEFAULT_DB=postgres
```

Названия переменных можно адаптировать под текущий проект, но в README нужно явно описать все переменные.

## 3.3. Docker Compose

`docker-compose.yml` должен запускать минимум три сервиса:

- Go-приложение;
- PostgreSQL;
- MySQL.

Должны быть отдельные volumes:

- `postgres_data`;
- `mysql_data`.

Приложение должно зависеть от обеих баз.

## 3.4. Миграции

Нужно обеспечить миграции для обеих СУБД.

Рекомендуемая структура:

```text
migrations/
  postgres/
    001_init.sql
    002_seed.sql
  mysql/
    001_init.sql
    002_seed.sql
```

Допустима другая структура, если обе базы поднимаются с нуля и README объясняет команды запуска.

## 3.5. Отличия SQL-диалектов

Нужно учитывать различия PostgreSQL и MySQL.

Примеры:

| Задача | PostgreSQL | MySQL |
|---|---|---|
| автоинкремент | `BIGSERIAL` | `BIGINT AUTO_INCREMENT` |
| boolean | `BOOLEAN` | `BOOLEAN` / `TINYINT(1)` |
| дата-время | `TIMESTAMPTZ` | `DATETIME` |
| JSON | `JSONB` | `JSON` |
| case-insensitive search | `ILIKE` | `LOWER(column) LIKE LOWER(?)` |
| placeholders | `$1`, `$2` | `?` |
| insert returning id | `RETURNING id` | `LastInsertId()` |
| upsert | `ON CONFLICT` | `ON DUPLICATE KEY UPDATE` |

Различия SQL-диалектов должны быть изолированы в repository/database layer.

Недопустимо хаотично размазывать проверки `if mysql/postgres` по handlers и templates.

# 4. Требования к database abstraction layer

## 4.1. Общий принцип

Handlers не должны напрямую знать технические детали подключения к PostgreSQL или MySQL.

Нужно реализовать единый способ получить repository/service для активной СУБД.

Допустимые подходы:

```go
type DBType string

const (
    DBPostgres DBType = "postgres"
    DBMySQL    DBType = "mysql"
)
```

```go
type DBProvider interface {
    GetDB(dbType DBType) (*sql.DB, error)
}
```

или factory:

```go
repo := repositories.NewRepository(activeDB, postgresDB, mysqlDB)
```

Можно использовать другой вариант, если он чистый и поддерживаемый.

## 4.2. Определение активной СУБД в запросе

В каждом HTTP-запросе нужно:

1. прочитать активную СУБД из cookie/session;
2. если значения нет — использовать `DEFAULT_DB`;
3. если значение некорректное — сбросить на `DEFAULT_DB`;
4. передать активную СУБД в service/repository layer;
5. передать `ActiveDB` в шаблон.

## 4.3. Отображение активной СУБД

Во всех базовых HTML-шаблонах должно быть видно:

```text
Активная БД: PostgreSQL
```

или:

```text
Активная БД: MySQL
```

# 5. Обязательное требование: редактирование абсолютно всех таблиц

Так как проект учебный, пользователь должен иметь возможность изменять через web-интерфейс **любую таблицу**, включая справочники.

## 5.1. Таблицы, которые обязательно должны иметь CRUD

CRUD нужен не только для основных сущностей, но и для всех справочников.

Обязательные справочники:

- `vehicle_class`;
- `vehicle_status`;
- `fuel_type`;
- `transmission_type`;
- `acquisition_type`;
- `maintenance_type`;
- `payment_type`;
- `contract_type`;
- `contract_status`.

Основные таблицы:

- `vehicle`;
- `driver`;
- `department`;
- `vehicle_assignment`;
- `trip_sheet`;
- `fuel_txn`;
- `maintenance_order`;
- `counterparty`;
- `contract`;
- `rental_event`.

Если в проекте есть `audit_log`, для неё нужно реализовать минимум:

- просмотр списка;
- просмотр карточки записи;
- фильтр по сущности/действию/дате.

Ручное редактирование `audit_log` можно не разрешать, если в интерфейсе явно написано, что журнал формируется автоматически.

## 5.2. CRUD для справочников

Для каждого справочника должна быть отдельная web-страница:

- список значений;
- добавление значения;
- редактирование значения;
- удаление значения;
- просмотр карточки значения, если такая модель уже есть в проекте.

Пример для `vehicle_class`:

```text
/vehicle-classes
/vehicle-classes/new
/vehicle-classes/{id}/edit
/vehicle-classes/{id}/delete
```

Маршруты можно адаптировать под существующий проект.

## 5.3. Нельзя скрывать справочники

Недопустимо:

- считать справочники служебными и не давать их редактировать;
- редактировать справочники только через SQL;
- редактировать справочники только через seed-файлы;
- разрешить редактирование только через прямой доступ к БД.

# 6. Кнопка `+` рядом со всеми связанными полями

## 6.1. Общий принцип

В формах создания и редактирования записей все поля, которые выбираются из другой таблицы, должны иметь рядом кнопку `+`.

Кнопка `+` открывает форму создания связанной записи.

Пример: создание автомобиля.

```text
Тип автомобиля: [легковой v] [+]
```

Если пользователь нажимает `+`, он попадает на страницу создания нового типа автомобиля. После создания нового типа, например `мотоцикл`, пользователь возвращается на форму создания автомобиля, где:

- все ранее введённые данные сохранены;
- новый тип `мотоцикл` уже доступен в выпадающем списке;
- желательно новый тип уже выбран автоматически.

## 6.2. Где обязательно нужны кнопки `+`

Кнопки `+` должны быть у всех foreign key / связанных dropdown-полей.

### Форма автомобиля `vehicle`

- `vehicle_class_id` → `+` создать класс автомобиля;
- `status_id` → `+` создать статус автомобиля;
- `fuel_type_id` → `+` создать тип топлива;
- `transmission_type_id` → `+` создать тип КПП;
- `acquisition_type_id` → `+` создать способ получения.

### Форма путевого листа `trip_sheet`

- `vehicle_id` → `+` создать автомобиль;
- `driver_id` → `+` создать водителя;
- `department_id` → `+` создать подразделение.

### Форма закрепления `vehicle_assignment`

- `vehicle_id` → `+` создать автомобиль;
- `driver_id` → `+` создать водителя;
- `department_id` → `+` создать подразделение.

### Форма заправки `fuel_txn`

- `vehicle_id` → `+` создать автомобиль;
- `payment_type_id` → `+` создать тип оплаты.

### Форма ТО/ремонта `maintenance_order`

- `vehicle_id` → `+` создать автомобиль;
- `maintenance_type_id` → `+` создать тип обслуживания.

### Форма договора `contract`

- `contract_type_id` → `+` создать тип договора;
- `counterparty_id` → `+` создать контрагента;
- `status_id` → `+` создать статус договора.

### Форма аренды `rental_event`

- `contract_id` → `+` создать договор;
- `vehicle_id` → `+` создать автомобиль.

## 6.3. Сохранение уже введённых данных

Это критическое требование.

Если пользователь начал заполнять форму, а потом нажал `+`, введённые данные не должны теряться.

Допустимые реализации:

### Вариант A. Session draft

Перед переходом на страницу создания связанной сущности JavaScript собирает текущие значения формы и отправляет их на endpoint сохранения черновика:

```text
POST /form-drafts
```

Затем пользователь переходит к созданию связанной сущности:

```text
/vehicle-classes/new?return_to=/vehicles/new&draft_id=abc123&field=vehicle_class_id
```

После создания справочника приложение возвращает пользователя:

```text
/vehicles/new?draft_id=abc123&selected_vehicle_class_id=12
```

### Вариант B. Query string draft

Можно передавать значения через query string, если форма небольшая. Для больших форм этот вариант хуже.

### Вариант C. Modal dialog

Можно реализовать создание справочника в модальном окне без ухода со страницы. После успешного создания нужно обновить dropdown и выбрать новое значение.

Любой вариант допустим, если пользователь не теряет уже введённые данные.

## 6.4. Возврат после создания связанной записи

После создания связанной записи приложение должно:

1. определить, откуда пришёл пользователь;
2. вернуть его на исходную форму;
3. восстановить введённые поля;
4. обновить нужный dropdown;
5. выбрать только что созданную запись, если это возможно.

# 7. Связанные выпадающие списки и каскадный поиск

## 7.1. Общий принцип

Поиск должен быть связанным, а не набором независимых полей.

Если значение одного поля ограничивает допустимые значения другого поля, второй dropdown должен показывать только релевантные значения.

Пример:

1. Пользователь выбирает ФИО водителя.
2. Поле `госномер автомобиля` показывает не все автомобили, а только автомобили, которые реально связаны с этим водителем.
3. После выбора автомобиля остальные поля поиска также ограничиваются по текущему контексту, если это возможно.

## 7.2. Обязательные каскадные связи

Нужно реализовать минимум следующие зависимые dropdown'ы:

- водитель → доступные автомобили;
- автомобиль → доступные водители;
- марка → модели;
- марка + модель → госномера;
- госномер → VIN;
- контрагент → договоры;
- договор → события аренды;
- автомобиль → путевые листы;
- автомобиль → заправки;
- автомобиль → ремонты;
- подразделение → связанные водители/автомобили, если связь есть в данных.

## 7.3. JSON-endpoints для зависимых списков

Нужно добавить JSON-endpoints для динамической подгрузки вариантов.

Примеры:

```text
GET /api/options/vehicles?driver_id=...
GET /api/options/drivers?vehicle_id=...
GET /api/options/models?make=...
GET /api/options/reg-numbers?make=...&model=...
GET /api/options/vins?reg_number=...
GET /api/options/contracts?counterparty_id=...
GET /api/options/rental-events?contract_id=...
GET /api/options/trip-sheets?vehicle_id=...&driver_id=...
GET /api/options/fuel-transactions?vehicle_id=...
GET /api/options/maintenance-orders?vehicle_id=...
```

Маршруты можно адаптировать под существующую архитектуру, но функциональность должна быть реализована.

## 7.4. Активная СУБД

Все JSON-endpoints обязаны учитывать активную СУБД пользователя.

- Если пользователь выбрал MySQL, каскадные списки строятся по данным MySQL.
- Если пользователь выбрал PostgreSQL, каскадные списки строятся по данным PostgreSQL.

# 8. Поиск не по ID, а по реальным пользовательским полям

## 8.1. Запрет на технический ID как основной поиск

Пользователь не должен быть вынужден помнить `id`.

Недопустимо делать основную форму поиска так:

```text
driver_id = 5
vehicle_id = 12
contract_id = 8
```

Внутри приложения можно использовать `id`, но в UI пользователь должен видеть понятные значения.

## 8.2. По каким полям искать

### Автомобили

Искать по:

- VIN;
- госномеру;
- марке;
- модели;
- году выпуска;
- классу;
- статусу;
- типу топлива.

### Водители

Искать по:

- ФИО;
- номеру водительского удостоверения;
- телефону.

### Путевые листы

Искать по:

- ФИО водителя;
- госномеру авто;
- марке/модели авто;
- подразделению;
- дате или периоду.

### Заправки

Искать по:

- госномеру авто;
- VIN;
- станции;
- типу оплаты;
- периоду;
- сумме;
- литрам.

### ТО/ремонты

Искать по:

- госномеру авто;
- VIN;
- типу обслуживания;
- сервису;
- дате открытия/закрытия;
- стоимости.

### Договоры

Искать по:

- номеру договора;
- контрагенту;
- типу договора;
- статусу;
- периоду.

### Аренда

Искать по:

- номеру договора;
- контрагенту;
- госномеру авто;
- периоду выдачи/возврата.

# 9. Маски, placeholder'ы и подсказки

## 9.1. Общий принцип

Во всех формах нужно добавить маски, placeholder'ы или подсказки, чтобы пользователь интуитивно понимал, что вводить.

Должна быть и клиентская, и серверная валидация.

## 9.2. Обязательные подсказки

### VIN

```text
Placeholder: XTA210990Y2760000
Ограничение: 17 символов
Подсказка: VIN должен содержать 17 символов
```

### Госномер

```text
Placeholder: А123ВС77
```

# 10. Требования к UI

## 10.1. Навигация

В интерфейсе должны быть разделы:

- Водители;
- Подразделения;

## 10.2. Раздел `Справочники`

Нужно добавить отдельную страницу, например:

```text
/lookups
```

На ней должны быть ссылки на CRUD всех справочников:

- классы автомобилей;
- статусы автомобилей;
- типы топлива;
- типы КПП;
- способы получения;
- типы ТО/ремонта;
- типы оплаты;
- типы договоров;
- статусы договоров.

## 10.3. Единообразие форм

Все формы должны иметь:

- заголовок;
- поля;
- кнопки `Сохранить`, `Отмена`, `Назад`;
- для связанных полей кнопку `+`;
- ошибки валидации;
- подсказки/placeholder'ы.

## 10.4. Табличные списки

Списки должны показывать не технические `id`, а человекочитаемые данные.

Плохо:

```text
id | vehicle_class_id | status_id
```

Хорошо:

```text
ID | Госномер | VIN | Марка | Модель | Класс | Статус | Пробег
```

ID можно оставить технической колонкой, но она не должна быть основным способом работы.

# 12. Требования к seed-данным

Нужно обеспечить seed-данные для обеих СУБД.

Seed-данные должны быть сопоставимыми:

- одинаковые справочники;
- одинаковые или очень близкие автомобили;
- одинаковые или очень близкие водители;
- одинаковые или очень близкие путевые листы;
- одинаковые или очень близкие заправки;
- одинаковые или очень близкие ремонты;
- одинаковые или очень близкие договоры.

Нужно иметь достаточно связанных данных, чтобы каскадные поиски реально работали.

Примеры данных:

- у одного водителя несколько связанных автомобилей;
- у автомобиля несколько путевых листов;
- у автомобиля есть заправки;
- у автомобиля есть ремонты;
- у контрагента несколько договоров;
- у договора есть события аренды.

# 15. Критерии приёмки

## 15.1. Две СУБД

Проект считается корректно обновлённым, если:

- `docker compose up` поднимает приложение, PostgreSQL и MySQL;
- PostgreSQL доступна и содержит нужные таблицы;
- MySQL доступна и содержит нужные таблицы;
- приложение подключается к обеим СУБД;
- пользователь может переключить активную СУБД через кнопку в web-интерфейсе;
- после переключения данные реально берутся из другой СУБД;
- CRUD работает в обеих СУБД;
- поиски работают в обеих СУБД;
- отчёты работают в обеих СУБД.

## 15.2. Все таблицы доступны через UI

- Есть CRUD для всех основных таблиц.
- Есть CRUD для всех справочников.
- Справочники не редактируются только через SQL.
- В интерфейсе есть отдельный раздел справочников.

## 15.3. Связанные поля

- Все foreign key поля в формах отображаются как dropdown с понятными значениями.
- У каждого такого dropdown есть кнопка `+`.
- Кнопка `+` открывает создание связанной записи.
- После создания связанной записи пользователь возвращается в исходную форму.
- Ранее введённые данные формы сохраняются.
- Новая связанная запись появляется в dropdown.

## 15.4. Поиск

- Основной поиск не требует знания `id`.
- Поиск использует ФИО, госномер, VIN, марку, модель, номер договора, контрагента, статус, даты и другие реальные поля.
- Связанные dropdown'ы фильтруются каскадно.
- При выборе водителя список автомобилей ограничивается связанными автомобилями.
- При выборе марки список моделей ограничивается выбранной маркой.
- При выборе контрагента список договоров ограничивается договорами контрагента.
- Все поиски учитывают активную СУБД.

## 15.5. UI и формы

- У полей есть placeholder'ы и подсказки.
- У дат используются `date` / `datetime-local` inputs.
- У числовых полей используются `number` inputs.
- VIN ограничен 17 символами.
- Стоимости, литры, пробег и год выпуска валидируются.
- Ошибки показываются пользователю.
- При ошибке введённые данные не теряются.
